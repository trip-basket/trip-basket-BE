# Error Handling Strategy

이 문서는 구현 상세 목록이 아니라, 프로젝트 전반에서 유지할 **에러 처리 정책/전략**을 정의합니다.

## 1. 목적

- 사용자에게 일관되고 이해 가능한 에러 응답을 제공한다.
- 내부 디버깅 정보가 외부로 노출되지 않도록 한다.
- 운영 관점에서 장애를 빠르게 분류하고 대응할 수 있게 한다.
- 기능이 늘어나도 문서를 자주 고치지 않도록, 클래스/엔드포인트 단위 나열 대신 원칙을 고정한다.

## 2. 에러 분류 전략

에러는 아래 3가지 범주로 다룬다.

1. Business Error
- 도메인 규칙 위반/리소스 상태 불일치
- 코드화된 `ErrorCode`를 통해 의미를 안정적으로 식별

2. Client/System 4xx Error
- 입력값 문제, 요청 형식 문제, 인증 토큰 형식 문제 등
- 사용자 수정 가능성이 높은 요청 오류

3. Server 5xx Error
- 예기치 못한 서버 장애, 외부 연동 실패, 설정 문제
- 운영자 대응이 필요한 시스템 오류

## 3. 응답 정책 (RFC 9457)

모든 에러 응답은 Problem Details(RFC 9457) 모델을 따른다.

핵심 정책:

- 표준 필드 사용: `type`, `title`, `status`, `detail`, `instance`
- 확장 필드(`props`): 검증 에러 상세처럼 클라이언트 UX에 필요한 경우만 사용
- `type` 전략:
  - 비즈니스 에러: `urn:problem:{stable-code}`
  - 일반 에러: 기본 타입(`about:blank`) 허용

메시지 정책:

- `detail`은 사용자 관점 문장으로 제공
- 내부 메시지, stacktrace, exception class name은 응답에 넣지 않음

## 4. 정보 노출 정책

응답에 노출 금지:

- `debugInfo`
- `cause` 체인
- 내부 구현 예외 메시지 원문
- stacktrace

응답에 노출 허용:

- 사용자 행동에 도움이 되는 메시지
- 요청 수정에 필요한 최소한의 구조화 정보(`errors`, `violations` 등)

## 5. 로깅 정책

### 5.1 분류

- Business 계열 로그: `BIZ-*` prefix
- System 계열 로그: `SYS-*` prefix

### 5.2 심각도

- `4xx`: `warn`, 요약 정보 위주, stacktrace 미출력
- `5xx`: `error`, stacktrace 출력

### 5.3 최소 로그 필드

운영 검색성과 상관관계 추적을 위해 다음 필드는 유지한다.

- status
- 에러 식별자(비즈니스 코드 또는 예외 클래스)
- message(내부 운영용)
- path

## 6. 구현 책임 분리 원칙

- `BusinessException`: 도메인 에러 의미와 내부 디버깅 컨텍스트를 전달
- `ErrorCode`: 상태/내부 메시지/사용자 메시지의 단일 소스
- `ErrorResponses`: RFC 9457 응답 형태 생성
- `GlobalExceptionHandler`: 예외 -> 응답/로그 정책 적용

핵심 원칙:

- **정책은 중앙화하고, 기능 상세 매핑은 코드에 둔다.**

## 7. 확장 가이드

새 기능에서 에러를 추가할 때는 아래 순서를 따른다.

1. 비즈니스 의미가 있는가?
- Yes: `ErrorCode` 추가 + `BusinessException` 사용
- No: 기존 시스템 예외 정책에 따라 핸들링

2. 클라이언트가 추가 맥락이 필요한가?
- Yes: `props`로 최소 데이터만 추가
- No: 표준 필드만 반환

3. 운영 추적에 식별자가 충분한가?
- 비즈니스: 코드로 식별 가능해야 함
- 시스템: 예외 유형 + 경로로 식별 가능해야 함

## 8. 문서 운영 원칙

이 문서는 전략 문서다. 따라서 아래 내용은 문서에 직접 나열하지 않는다.

- 특정 기능의 세부 예외 클래스 목록
- 기능별 상태 코드 매핑의 전체 표
- 개별 API 예시 응답 다수

해당 상세는 코드/테스트/릴리즈 노트에서 관리한다.
