# API Conventions

이 문서는 API 설계 시 지켜야 할 **공통 규약**을 정의합니다.

세부 에러 구현/로깅 정책은 [error-handling.md](./error-handling.md)를 기준으로 합니다.

## 1. 설계 원칙

- 일관성: 기능이 달라도 같은 형태의 URI, 상태 코드, 응답 규칙을 유지한다.
- 예측 가능성: 클라이언트가 에러/성공 케이스를 동일한 방식으로 해석할 수 있어야 한다.
- 최소 노출: 내부 구현 세부사항은 응답에서 숨기고, 사용자 행동에 필요한 정보만 제공한다.
- 확장성: 기능 추가 시 기존 계약을 깨지 않도록 한다.

## 2. URI & 메서드 규약

- 리소스 중심 URI를 사용한다: `/api/{resource}`
- HTTP 메서드는 의미에 맞게 사용한다: `GET`, `POST`, `PUT/PATCH`, `DELETE`
- URI에는 동사 대신 리소스 명사를 사용한다.
- 경로 파라미터는 식별자, 쿼리 파라미터는 필터/정렬/페이지네이션 용도로 사용한다.

## 3. 인증/인가 규약

- 기본 인증 방식은 쿠키 기반 JWT 인증이다.
- 인증 필요 API는 Security 설정에서 중앙 관리한다.
- 인증 실패/토큰 문제는 `401` 정책으로 일관 처리한다.

## 4. 요청 규약

- `Content-Type: application/json`을 기본으로 한다.
- 입력 검증은 컨트롤러 경계에서 수행한다.
- 잘못된 입력은 `4xx`로 반환하며, 수정 가능한 정보를 명확히 제공한다.

## 5. 성공 응답 규약

- 성공 응답은 기본적으로 리소스/결과 DTO를 직접 반환한다.
- 팀 합의 전까지 성공 응답 공통 envelope는 강제하지 않는다.
- 상태 코드는 의미 기반으로 사용한다.
  - `200`: 조회/처리 성공
  - `201`: 생성 성공
  - `204`: 본문 없는 성공

## 6. 에러 응답 규약 (요약)

- 에러 응답은 RFC 9457 Problem Details를 따른다.
- 기본 필드: `type`, `title`, `status`, `detail`, `instance`
- 추가 정보가 필요한 경우에만 extension member(`props`)를 사용한다.
- 비즈니스 에러는 안정적인 타입 식별자를 사용한다(`urn:problem:*`).

상세 규칙은 [error-handling.md](./error-handling.md) 참조.

## 7. 상태 코드 사용 원칙

- `4xx`: 클라이언트 요청 수정으로 해결 가능한 오류
- `5xx`: 서버/외부 시스템/설정 문제로 운영 대응이 필요한 오류
- 같은 원인에는 항상 같은 범주의 상태 코드를 사용한다.

## 8. 호환성/버전 정책

- 기존 클라이언트 계약을 깨는 변경은 지양한다.
- 불가피한 변경은 마이그레이션 경로와 공지 일정을 함께 제공한다.
- 메시지 문구 변경보다 필드/스키마 안정성을 우선한다.

## 9. 문서화 정책

- 공개 API는 OpenAPI(스웨거)로 문서화한다.
- 컨트롤러에 최소한의 성공/에러 시나리오를 어노테이션으로 유지한다.
- 상세 동작(예외 종류, 내부 로깅 형식)은 구현 문서로 분리한다.

## 10. 신규 API 추가 체크리스트

- URI가 리소스 중심 규칙을 따르는가?
- 인증 필요 여부가 보안 정책에 반영되었는가?
- 입력 검증 실패 시 `4xx`와 에러 본문 규약을 지키는가?
- 성공/실패 상태 코드가 의미에 맞는가?
- OpenAPI 문서가 최신 상태인가?
